## 1. Overview

This document defines the formal JSON Schemas for all RabbitMQ messages in MageCode 2.0. It reflects the final inter-service communication architecture established by Decision Log v3 (D-80 through D-89).

### 1.1. Key Architectural Context

MageCode uses two distinct processing paths (D-80, D-81):

- **Real-time path (CES):** Student submits → CES has direct DB access → writes results to DB → signals api via `result-execution` queue → api pushes WebSocket to student.
- **Batch path (SIM/AID/VUL):** GV triggers → api publishes jobs with full info → stateless workers process → return full results via `result-analysis` queue → api writes all results to DB → pushes WebSocket to GV.

### 1.2. Queue Map (6 Queues)

| Queue | Direction | Producer | Consumer | Pattern |
|---|---|---|---|---|
| `code-executor` | Job | api | CES | 1 message per submission |
| `plagiarism-checker` | Job | api | SIM | 1 message per language group in batch |
| `ai-detector` | Job | api | AID | 1 message per analysis_submission |
| `vuln-scanner` | Job | api | VUL | 1 message per analysis_submission |
| `result-execution` | Result | CES | api | 1 message per completed submission |
| `result-analysis` | Result | SIM/AID/VUL | api | Discriminated union on `service` field |

### 1.3. Schema Files

| File | Queue | Direction |
|---|---|---|
| `job.code-executor.v1.schema.json` | code-executor | api → CES |
| `job.plagiarism-checker.v1.schema.json` | plagiarism-checker | api → SIM |
| `job.ai-detector.v1.schema.json` | ai-detector | api → AID |
| `job.vuln-scanner.v1.schema.json` | vuln-scanner | api → VUL |
| `result.execution.v1.schema.json` | result-execution | CES → api |
| `result.analysis.v1.schema.json` | result-analysis | SIM/AID/VUL → api |

## 2. Conventions

### 2.1. Common Fields

Every message MUST include these 3 fields:

| Field | Type | Description |
|---|---|---|
| `trace_id` | UUID string | Cross-service tracing ID. Generated by api when creating the job. Echoed back in result messages. Used for unified log querying in Loki (D-88). |
| `timestamp` | ISO 8601 UTC string | Time the message was published. |
| `version` | String `"1.0"` | Schema version. See §2.4 for versioning policy. |

### 2.2. Delivery & Encoding

- **Delivery mode:** Persistent (`delivery_mode = 2`) for all messages.
- **Content type:** `application/json`, encoding UTF-8.
- **Acknowledgement:** Manual ack. Consumer acks after successful processing. Nack + requeue only for transient infrastructure errors (RabbitMQ reconnect, container restart).

### 2.3. additionalProperties Policy (Asymmetric)

- **Job messages (api → services):** `additionalProperties: false` — strict validation. Catches typos and malformed messages at the producer. Safe because deploy order is controlled: update consumers (services) first, then producer (api).
- **Result messages (services → api):** `additionalProperties` NOT restricted — forward compatible. During rolling deploy, a newer service version may include extra fields that older api versions must ignore gracefully.

### 2.4. Schema Versioning

- **Minor bump (1.0 → 1.1):** Add optional fields only. Backward compatible. Result consumers MUST ignore unknown fields. Job consumers MAY reject unknown fields.
- **Major bump (1.0 → 2.0):** Breaking change (remove required fields, change types, change semantics). Requires coordinated deploy or dual-queue strategy.
- **Consumer behavior:** MUST reject messages where `parseInt(version) != expected_major`. SHOULD accept any minor version ≥ expected.

### 2.5. Error Handling Convention

- Services MUST retry transient errors internally (network timeout, MinIO unavailable) with exponential backoff, max 3 retries.
- Services publish `status: "error"` only after exhausting retries — api always treats errors as permanent.
- `error_message` is optional and for debugging only — api logs it but does not display to users.

### 2.6. MinIO Pre-signed URLs

- TTL: **6 hours** (covers max queue wait time + 30min analysis timeout + buffer).
- SIM/AID/VUL MUST download files at the start of processing and work with local copies.
- CES accesses MinIO directly with credentials (D-85) — no pre-signed URL needed.

### 2.7. Service Identifiers (D-26)

String enum values used in `service` field:

| Identifier | Service | Abbreviation |
|---|---|---|
| `code-executor` | Code Execution Service | CES |
| `plagiarism-checker` | Plagiarism Check Service | SIM |
| `ai-detector` | AI Detection Service | AID |
| `vuln-scanner` | Vulnerability Scan Service | VUL |

## 3. Job Messages (api → services)

### 3.1. Queue: `code-executor`

**Pattern:** 1 message per submission.
**Trigger:** Student submits code → api creates submission record → publishes message.
**Why ID-only:** CES has direct DB access (D-81) — reads test cases, programming language, and file path from DB.

```json
{
  "submission_id": 1042,
  "trace_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timestamp": "2026-09-15T08:30:00Z",
  "version": "1.0"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `submission_id` | integer ≥ 1 | Yes | PK of `submissions` table |
| `trace_id` | UUID string | Yes | Cross-service tracing ID |
| `timestamp` | ISO 8601 string | Yes | Publish time |
| `version` | `"1.0"` | Yes | Schema version |

### 3.2. Queue: `plagiarism-checker`

**Pattern:** 1 message per language group within an analysis batch.
**Trigger:** GV triggers analysis with SIM enabled → api groups submissions by language → publishes 1 message per language group.
**Why grouped by language:** Dolos requires a single language per run. Cross-language plagiarism comparison is not meaningful in education context.

**api publishing logic:**
1. Collect all submissions in scope (semester-level, all sections with equivalent problems).
2. Group by `programming_languages.dolos_language`.
3. For each group with ≥ 2 submissions: publish 1 message.
4. For groups with < 2 submissions: do NOT publish. Set `analysis_submissions.plagiarism_status = 'not_applicable'` for those submissions.
5. Set `language_group_total` = number of groups published. If 0 groups qualify, mark SIM completed immediately.

```json
{
  "analysis_problem_id": 45,
  "language": "python",
  "language_group_index": 0,
  "language_group_total": 2,
  "submissions": [
    {
      "submission_id": 101,
      "analysis_submission_id": 501,
      "file_url": "https://minio.local/submissions/101/main.py?X-Amz-Credential=..."
    },
    {
      "submission_id": 102,
      "analysis_submission_id": 502,
      "file_url": "https://minio.local/submissions/102/main.py?X-Amz-Credential=..."
    },
    {
      "submission_id": 203,
      "analysis_submission_id": 503,
      "file_url": "https://minio.local/submissions/203/solution.py?X-Amz-Credential=..."
    }
  ],
  "trace_id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "timestamp": "2026-09-15T14:00:00Z",
  "version": "1.0"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `analysis_problem_id` | integer ≥ 1 | Yes | PK of `analysis_problems` table |
| `language` | enum: `python`, `java`, `c`, `cpp` | Yes | Dolos language for this group |
| `language_group_index` | integer ≥ 0 | Yes | 0-based index of this group in batch |
| `language_group_total` | integer ≥ 1 | Yes | Total groups published for this batch |
| `submissions` | array (min 2 items) | Yes | Submissions to compare |
| `submissions[].submission_id` | integer ≥ 1 | Yes | PK of `submissions` table |
| `submissions[].analysis_submission_id` | integer ≥ 1 | Yes | PK of `analysis_submissions` table |
| `submissions[].file_url` | URI string | Yes | MinIO pre-signed URL (TTL 6h) |
| `trace_id` | UUID string | Yes | Cross-service tracing ID |
| `timestamp` | ISO 8601 string | Yes | Publish time |
| `version` | `"1.0"` | Yes | Schema version |

|---|---|---|---|

| `file_url` | URI string | Yes | MinIO pre-signed URL (TTL 6h) |

## 4. Result Messages (services → api)

### 4.1. Queue: `result-execution`

**Direction:** CES → api.
**Pattern:** 1 message per completed submission.
**Purpose:** Signal for api to push WebSocket to student. CES has already written all results to DB (D-81).
**Why include execution_status + counts:** Saves api from querying DB just to push a WebSocket notification. Reduces latency for real-time UX.

```json
{
  "submission_id": 1042,
  "service": "code-executor",
  "status": "completed",
  "execution_status": "partially_accepted",
  "testcases_passed": 7,
  "testcases_total": 10,
  "trace_id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "timestamp": "2026-09-15T08:30:12Z",
  "version": "1.0"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `submission_id` | integer ≥ 1 | Yes | PK of `submissions` table |
| `service` | `"code-executor"` | Yes | Fixed value |
| `status` | enum: `completed`, `error` | Yes | Processing outcome. `completed` = all test cases processed. `error` = system failure. |
| `execution_status` | enum: `accepted`, `partially_accepted`, `error`, `timeout`, `language_not_supported` | Yes | Submission-level status (mirrors DB) |
| `testcases_passed` | integer ≥ 0 | Yes | Count of accepted test cases |
| `testcases_total` | integer ≥ 0 | Yes | Total test cases executed |
| `error_message` | string | No | Error detail when `status=error` |
| `trace_id` | UUID string | Yes | Echoed from job message |
| `timestamp` | ISO 8601 string | Yes | Publish time |
| `version` | `"1.0"` | Yes | Schema version |

### 4.2. Queue: `result-analysis`

**Direction:** SIM/AID/VUL → api.
**Discrimination:** api reads `service` field to determine message format.
**DB writes:** api is the single writer for all batch analysis results (D-80).

#### 4.2.1. SIM Result (`service: "plagiarism-checker"`)

**Pattern:** 1 message per language group (echoes `language_group_index` / `language_group_total` from job).
**Completion tracking:** api counts received results per `analysis_problem_id`. When count == `language_group_total`, SIM is done for this batch.
**match_type not included:** SIM does not know section membership. api assigns `WITHIN_SECTION` / `CROSS_SECTION` when writing to DB based on `submission.problem.section_id`.

```json
{
  "analysis_problem_id": 45,
  "service": "plagiarism-checker",
  "status": "completed",
  "language": "python",
  "language_group_index": 0,
  "language_group_total": 2,
  "pairs": [
    {
      "submission_a_id": 101,
      "submission_b_id": 102,
      "similarity": 0.8734,
      "longest_fragment": 45,
      "total_overlap": 120,
      "a_regions": "5,1,12,40|20,1,25,35",
      "b_regions": "8,1,15,40|30,1,35,35"
    },
    {
      "submission_a_id": 101,
      "submission_b_id": 203,
      "similarity": 0.1205,
      "longest_fragment": 8,
      "total_overlap": 15,
      "a_regions": null,
      "b_regions": null
    },
    {
      "submission_a_id": 102,
      "submission_b_id": 203,
      "similarity": 0.0832,
      "longest_fragment": 5,
      "total_overlap": 9,
      "a_regions": null,
      "b_regions": null
    }
  ],
  "submission_statuses": [
    { "analysis_submission_id": 501, "status": "completed" },
    { "analysis_submission_id": 502, "status": "completed" },
    { "analysis_submission_id": 503, "status": "completed" }
  ],
  "trace_id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
  "timestamp": "2026-09-15T14:02:30Z",
  "version": "1.0"
}
```

| Field | Type | Required | Description |
|---|---|---|---|
| `analysis_problem_id` | integer ≥ 1 | Yes | PK of `analysis_problems` table |
| `service` | `"plagiarism-checker"` | Yes | Discriminator |
| `status` | enum: `completed`, `error` | Yes | Batch-level outcome for this language group |
| `error_message` | string | No | Error detail |
| `language` | enum: `python`, `java`, `c`, `cpp` | Yes | Echoed from job |
| `language_group_index` | integer ≥ 0 | Yes | Echoed from job |
| `language_group_total` | integer ≥ 1 | Yes | Echoed from job |
| `pairs` | array of pair objects | Yes | Pairwise results (empty if error) |
| `pairs[].submission_a_id` | integer ≥ 1 | Yes | First submission (always < b) |
| `pairs[].submission_b_id` | integer ≥ 1 | Yes | Second submission (always > a) |
| `pairs[].similarity` | number 0.0–1.0 | Yes | Similarity score |
| `pairs[].longest_fragment` | integer or null | No | Longest matching fragment (tokens) |
| `pairs[].total_overlap` | integer or null | No | Total overlapping tokens |
| `pairs[].a_regions` | string or null | No | Highlight regions, pipe-separated |
| `pairs[].b_regions` | string or null | No | Highlight regions, pipe-separated |
| `submission_statuses` | array | Yes | Per-submission processing status |
| `submission_statuses[].analysis_submission_id` | integer ≥ 1 | Yes | PK of `analysis_submissions` |
| `submission_statuses[].status` | enum: `completed`, `error` | Yes | Per-submission outcome |
| `submission_statuses[].error_message` | string | No | Per-submission error detail |
| `trace_id` | UUID string | Yes | Echoed from job |
| `timestamp` | ISO 8601 string | Yes | Publish time |

## 5. api Consumer Logic

### 5.1. result-execution Consumer

```
1. Receive message from result-execution queue
2. Parse, validate required fields
3. Push WebSocket to student:
   - Channel: private-submission.{submission_id}
   - Event: execution.completed
   - Payload: { execution_status, testcases_passed, testcases_total }
4. Ack message
```

No DB write needed — CES already wrote everything.

### 5.2. result-analysis Consumer

```
1. Receive message from result-analysis queue
2. Read service field → route to handler

IF service = "plagiarism-checker":
   a. Write each pair to similarity_results table
      - Assign match_type based on section membership:
        sectionA = submissionA.problem.section_id
        sectionB = submissionB.problem.section_id
        match_type = (sectionA == sectionB) ? 'WITHIN_SECTION' : 'CROSS_SECTION'
   b. Update analysis_submissions.plagiarism_status per submission_statuses[]
   c. Track completion: increment SIM result counter for this analysis_problem_id
   d. If counter == language_group_total → SIM phase done for this batch

IF service = "ai-detector":
   a. Write to ai_detection_results table (probability)
   b. Update analysis_submissions.ai_detection_status

IF service = "vuln-scanner":
   a. Write each finding to vulnerability_results table
   b. Update analysis_submissions.vuln_scan_status

THEN (for all services):
   c. Check if ALL enabled services completed for this analysis_submission
   d. If yes → mark analysis_submission.completed_at
   e. Check if ALL analysis_submissions completed for this analysis_problem
   f. If yes → mark analysis_problem.status = 'completed', completed_at = now()
   g. Push WebSocket to GV:
      - Channel: private-analysis.{analysis_problem_id}
      - Event: analysis.updated (partial) or analysis.completed (all done)
   h. Ack message
```

### 5.3. SIM Completion Tracking Detail

api maintains a counter (in-memory or Redis) per `analysis_problem_id`:

```
Key: sim_completion:{analysis_problem_id}
Value: { received: 0, total: language_group_total }

On each SIM result:
  received++
  if received == total → SIM phase complete for this batch
```

If api restarts mid-tracking, the counter is lost. Recovery: scheduled timeout job (D-82) catches stuck batches after 30 minutes. Acceptable because SIM results are idempotent — if re-triggered, old results are replaced.

## 6. Decision Traceability

| Decision | Schema Impact |
|---|---|
| D-26 String enums | All `service`, `status`, `execution_status` fields use string values |
| D-80 Stateless SIM/AID/VUL | Job messages carry full info: `file_url`, `language`. Result messages carry full result data. |
| D-81 CES keeps DB | CES job = ID only. CES result = signal only (data already in DB). |
| D-83 Split result queues | `result-execution` (CES→api) + `result-analysis` (SIM/AID/VUL→api) |
| D-84 Job message payload | CES: ID only. Others: full info + file_url. |
| D-85 Pre-signed URLs | `file_url` in SIM/AID/VUL jobs. TTL 6h. CES direct access. |
| D-88 trace_id | Required in every message. UUID format. Generated by api. |
| Multi-language batch | SIM jobs split by language. `language_group_index/total` for tracking. |
| Asymmetric additionalProperties | Job messages strict, result messages loose (forward compatible). |

## 7. Known Limitations & Future Considerations

### 7.1. SIM Message Size (Deferred to Phase 3)

For large batches (150+ submissions, 11K+ pairs with regions), SIM result message may reach several MB. RabbitMQ handles this (default max 128MB) but performance degrades with very large messages.

**Mitigation when needed:** SIM writes result to MinIO as JSON file, result message contains `result_file_url` instead of inline data. Requires api to provide a pre-signed upload URL in job message. Track as enhancement for Phase 3 if actual deployment shows message size issues.

### 7.2. Language Enum Expansion

When adding new programming languages (Go, JavaScript, Rust, etc.): update `language` enum in job schemas, add entries to `programming_languages` seed table, and verify Dolos/CodeQL/CodeBERT support. No structural schema change needed.

### 7.3. Fifth Analysis Service (v3.0)

If a 5th analysis service is added: add new job queue, add new `$def` variant to `result-analysis` schema, and refactor `analysis_submissions` per-service columns into a separate `analysis_service_statuses` table (noted as intentional tech debt in Database Schema v2).
